# プロジェクトメモ

## 作業ルール（徹底）
- 依頼された内容に関係のないファイルには一切手を触れない。
- 既存機能を壊さないよう慎重に進める（変更後は関連するスモークテストで確認してから完了とする）。
- 想定外の事態（イレギュラー）が起きた場合は、その都度ユーザーに相談してから進める。

## 実装済み
- **Tee残高不足チェック**: 公開募集を新規開始する際、残高 < 掲載費用（perEntryTeeCost）だと「公開募集を開始する」ボタンが無効化される。不足額とチャージ導線（残高モーダルを開く）を表示。既存の公開募集の設定変更（再課金なし）には適用しない。
- **公開募集の課金モデル**: 掲載開始時には課金しない。応募（エントリー）が1件入るたびにperEntryTeeCost（10Tee）を課金する（`applyToShift`/`enterRecruitShift`）。
- **PDF発行課金**: 給料明細書発行・請求書発行はそれぞれ1発行1Teeで課金。給料明細書は同じ対象月への再発行は課金済みのため無料（`historySalaryByMonth[month].issued`で判定）。請求書は発行のたびに新しい請求内容のため都度課金（同一請求書を再ダウンロードするUIは未実装）。残高不足時はどちらも発行ボタンが無効化され、警告を表示。

## 未実装・既知の制約
- **他社シフトとの重複警告（スタッフ自己応募時）**: 会社側がシフトを作成・アサインする際は`timeRangesOverlap`による重複チェックと警告が働くが、スタッフが公開募集に自分で「希望を出す」フロー（`applyToShift`/`enterRecruitShift`）には重複チェックが一切なく、他の勤務先の確定シフトと時間が被っていても警告なく提出できてしまう。未実装。
- **招待URLの実際の遷移**: 「招待する」ボタンはコピー用URL文字列を発行するのみで、実際にそのURLを開いた側のアカウント作成〜自動参加（スタッフ／依頼主／派遣会社として）は未シミュレーション。現状のログイン画面から「アカウント作成」をすると招待経路に関わらず必ず「本部を作成する」画面に案内されるため、招待されたスタッフが会社作成を求められる形になる（本来は所属先へ自動参加してスタッフ画面に入るべき）。プロトタイプの制約として許容し、実装しない。

## 決定事項（変更しない前提）
- 会社のTee残高とスタッフのポイント残高は別管理（`ticketRemaining` / `staffPoints`）。混同させない。
- 派遣会社と派遣先のTeeウォレットは現状共有のまま（デモ簡略化として許容、本実装時は要検討）。
- 景品の配送は配送業者API連携なし。管理者が手動で「発送済み」にする運用で十分（低単価・低頻度のため）。
- チャージ方法はクレジットカード（即時反映）と銀行振込（着金確認後に反映、着金前はTee付与しない）。
- 会社機能は「自社スタッフのシフト管理・業務報告承認」が全社共通の土台（トグル不要）。「他社へスタッフを派遣する」がONの時だけ取引先管理・請求書作成が使える追加機能。「派遣先」として受け入れる側は土台機能だけで完結し、受け取った請求書をアプリ内で確認・承認する機能は持たない（派遣会社側が土台機能に追加トグルを乗せたものが「派遣先」という別モジュールではない、という整理）。
- 請求書・給与明細はPDFを発行してメール/LINE等アプリ外で送付する運用とし、受け取り側がアプリ内で確認する機能は作らない。発行側には発行したPDFの履歴（再ダウンロード・再送用）と、修正した場合の修正履歴を残す。
